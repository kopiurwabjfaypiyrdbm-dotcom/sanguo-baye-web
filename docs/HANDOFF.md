# 项目交接：sanguo-baye-web

更新日期：2026-07-26

## 1. 项目目标

本项目是对步步高电子词典版《三国霸业》的现代 Web 重写，不是给现有 WASM 移植版重新套一层界面。

长期方向是：以固定版本的 C 移植核心和可重复运行结果为规则事实源，在 TypeScript 中逐步重写规则层；用 React 与 Phaser 提供现代化、可维护的表现；在不分发来源不明原版资产的前提下，最终形成完整可玩的游戏。

现阶段的决策原则是“产品进度优先、在实现过程中验证原版”。技术底座已经能够支持持续开发，不应重新回到长时间只研究、不增加可玩内容的状态。

## 2. 当前玩家可体验的内容

应用已经形成可连续游玩的战略层闭环：

- 标题屏支持“新君登基”和从自动存档“重返沙场”。
- 可选择董卓弄权、曹操崛起、赤壁之战、三国鼎立四个时期，再选择君主开始战役。
- 四个时期均使用随应用发布的结构化数据，可进入 38 城完整战略地图，不需要玩家选择本地 `.lib` 文件。
- 地图支持拖动、缩放、城市选择和势力颜色反馈。
- 玩家可执行开垦、征兵、兵力分配、搜寻、登用、赏金、道具赏赐与装备管理、相邻城市调动、太守任命和出征。
- 月末会执行战略 AI、资源结算、体力恢复、年月推进、胜负判定和事件摘要。
- 支持自动存档、3 个本地手动槽、JSON 导入和导出。
- 相同状态、命令和随机种子会产生相同结果。
- 玩家出征可选择快速结算或进入 Phaser 手动战场，完成移动、普通攻击、待命、敌方基础 AI 和胜负结算后返回战略地图。
- AI 进攻玩家城市时会暂停月度推演，让玩家手动守城；战斗结束后从下一 AI 势力继续推演。
- 战术 v0.2 已加入按进攻方向部署、两类结构化战场、原版六兵种基础移动力、河流/山林通行差异、路径和伤害预览、占城阶段确认、明确胜因与改进的确定性 AI。
- 战略节奏已把所有在职势力对称设为 400 开局兵力，取消玩家 100/AI 800 的旧临时不对称；同时增加公平的单次增兵上限，并提高开局月 AI 出征阈值。
- 兵力分配会消耗武将当月行动，不能通过重复分配绕过单次上限；势力失去最后一城后，其全部在职武将转为无所属在野，避免残留在敌方城市。
- 手动战场当前每方最多部署 10 名武将；战斗相关人物数值在状态入口要求有限、非负整数，避免非法存档进入兼容公式后崩溃。
- 四时期的 33 项临时道具目录、隐藏/已发现城池库存和人物初始双槽装备已经进入状态；搜寻可发现道具，赏赐可装备物品或消耗兵符改变兵种，AI 也会使用已发现道具，装备有效属性进入战略与手动战斗。目录内容来自仓库早期整理表，重新关联固定上游前不宣称原版内容一致。

内置 12 城示例状态仍作为测试夹具保留；正式开局流程默认使用四时期完整剧本。

## 3. 当前尚未完成的关键内容

手动战术战斗 v0.2 已可玩，但距离原版完整战场仍有较大差距。当前战场使用来源明确的现代结构化地图和改进后的确定性启发式 AI，已接入原版基础移动力，但尚未接入原版战场编号对应的地图、`dFgtLandR` 精确地形通行表、`dFgtAtRange` 完整攻击范围、技能、天气、异常状态、单挑和经验成长。

其他主要缺口：

- 城市命令、月度结算和战略 AI 中仍有现代临时公式，不能声明为原版一致。
- 原版的命令队列、按道路距离移动、完整人才登场条件尚未接入。
- 道具基础闭环已形成，并已切换为原版顺序的两个通用装备位；道具伯乐条件、战后缴获、更完整的 AI 配装以及 33 项目录内容的固定来源重关联仍待接入。
- 战术技能、完整状态、原版地形地图、原版战斗 AI 和战后俘虏等系统尚未完成。
- 外交、时期事件、人物关系及更完整的历史演进尚未实现。
- 当前视觉是现代化信息原型，尚未进入正式美术生产和移动端专项适配。

准确的原版兼容状态以 `references/parity-matrix.md` 为准。README 中的功能描述是玩家能力摘要，不能替代一致性证据。

## 4. 建议的接手重点

下一阶段建议在保持现有手动战斗闭环可玩的前提下，把临时战术规则分批替换为原版证据支持的规则。优先级依次是：原版移动与攻击范围、战场部署和目标条件、粮草/战斗日语义、固定战场 AI 决策样本，然后再进入技能、状态与天气。

产品侧应同步改善战场可读性和反馈：明确当前可行动单位、移动路径、预计伤害、攻守目标和战斗日志，并为多武将战斗补充更顺畅的阶段操作。原版地图资源的许可边界未解决前，继续使用来源明确、可替换的结构化战场，不得提交原版地图数组或图片。

## 5. 技术结构

```text
src/core/          战略领域状态、命令、AI、经济、战斗、回合、存档和校验
src/compat/baye/   有独立参考输出支持的原版兼容算法
src/data/          四时期数据、CSV/JSON 与原版资源解析转换
src/game/          Phaser 场景、战略地图和 React/Phaser 事件桥
src/ui/            React 开局流程、城池面板和应用编排
references/        上游锁定、来源边界、一致性矩阵、夹具和研究记录
data/source/       可编辑的数据整理表
docs/design/       已确认的设计和兼容策略
```

重要边界：

- `src/core/` 负责规则和状态变更，UI 不复制合法性判断或数值公式。
- `src/compat/baye/` 只保存经过原版源码或独立输出支持的兼容实现。
- React 管理应用流程和面板，Phaser 管理画布场景；两者通过显式事件和状态更新通信。
- 规则函数延续不可变状态更新，并在完整操作后执行状态校验。
- `GameState.rngSeed` 是确定性推演的一部分，新增随机行为必须保存并推进种子。

继续战斗开发时，从这些入口开始：

- `src/core/battle.ts`：快速结算、战斗结果与战略原子回写。
- `src/core/tacticalBattle.ts`：手动战斗状态、移动、普通攻击、阶段、基础 AI、胜负与结果生成。

- `src/game/createBattleGame.ts` 与 `src/game/BattleScene.ts`：Phaser 手动战场和生命周期。
- `references/vendor/baye-c-core/src/Fight.c`、`FightSub.c`、`FgtCount.c`、`FgtPkAi.c`：战场进入、行为、计算和 AI 参考。

## 7. 本地运行与验证

环境要求：Node.js 20 或更高版本。

首次拉取或依赖锁变化后：

```bash
npm ci
npm run check
```

日常开发：

```bash
npm run dev
```

`npm run check` 是一次性验证命令，不是常驻服务。它会依次验证已入库参考源码的提交与哈希、并行运行 Vitest，并执行 TypeScript 和 Vite 生产构建；短暂使用多个 CPU 核心属于正常现象，完成后所有测试工作进程应退出。当前交接基线为 139 项测试通过、4 项需要额外参考条件的测试跳过，生产构建通过。

只能保留一个 `npm run dev`。Vite 开发服务器会持续监视仓库文件，应在原终端按 `Ctrl+C` 关闭。项目启用了严格端口检查；若端口占用，应复用或关闭原实例，不要改用连续的新端口启动多个服务器。

Vite 当前会提示主 JavaScript 包超过 500 kB；这是已知的非阻塞警告。引入新的大型战场模块时应考虑按场景动态加载，但不要在战术闭环之前展开无目标的性能重构。

## 8. 原版参考资料和许可证边界

日常需要的 51 个 MIT C 规则与结构源码已经入库：

```text
references/vendor/baye-c-core/
```

它们绑定 `references/upstream-lock.json` 中的固定提交，并由 `MANIFEST.json` 保存逐文件哈希。普通开发不需要初始化额外参考。

只有更新 vendored 基线时才顺序执行：

```bash
npm run reference:setup
npm run reference:sync-core
npm run reference:check
```

仅研究额外资料时，从下列级别选择一个，不能顺序执行：

```bash
npm run reference:setup          # 少量补充参考
npm run reference:setup:full     # 完整 C 工程和技术文档
npm run reference:setup:offline  # 完整参考再加 GPL 离线运行壳
```

这些互斥命令把资料放到被 Git 忽略的 `.reference/`。`reference:setup:offline` 会显式获取 GPL 离线运行壳，只能作为本地参考。

禁止提交或混入正式产品的内容包括：`dat.lib.orig`、其他 `.lib`、字体、原版图片、音视频、WASM、内嵌原版资源数组，以及未确认独立再分发许可证的技术文档。四时期 `baye-periods.json` 是已解析的结构化运行数据，不包含上述原始文件。

## 9. 存档与兼容注意事项

- 当前 `GameState.schemaVersion` 为 2，存档通过版本化 envelope 管理。
- 修改 `GameState` 的持久字段时，必须同时处理序列化、解析、迁移、完整性校验和测试。
- 应用在战略状态更新后覆盖自动存档。AI 进攻玩家时，`saveStorage.ts` 另保存战前战略检查点、待执行攻击和 AI 恢复游标；连续守城之间会覆盖为新的检查点。
- 当前不支持战中存档。玩家主动进入战斗前会覆盖当前战役的自动存档，刷新后回到战前战略地图；AI 守城战则从战前检查点重新开始。战术局面不会被序列化，战斗结果只在完成后原子写回战略状态。
- 战斗结果只能应用一次，并应拒绝随机种子、回合或城池归属已经变化的陈旧结果。

## 10. 已知易踩点

- `executeAttack()` 当前直接完成战斗并修改战略状态；接入手动战场时应拆分“验证并创建战斗”与“完成后应用结果”，不要在 UI 复制现有校验。
- 自动存档由 React 状态更新触发。新增短暂 UI 状态不必进入 `GameState`，但影响可恢复玩法的状态必须有明确持久化策略。
- 原版时期人物包含在职、在野和未登场状态；不能假设每个人都有势力或城市。
- 中立城市使用非玩家中立势力桶，不获得普通 AI 回合。
- Phaser 战略地图由 React 创建一次，再通过 controller 更新。新增战场场景时需要明确场景销毁和返回地图的生命周期。
- 上游存在 Windows 保留文件名 `con.py`；参考初始化脚本已经通过安全落盘规避，不要恢复为直接稀疏检出整个工作树。
- “测试通过”不等于“原版一致”。一致性状态必须同时有源码定位或可重复参考输出。

## 11. 交接完成条件

接手者在开始修改前应能够：

- 使用 `npm run check` 复现绿色基线。
- 不依赖个人磁盘路径，在 `references/vendor/baye-c-core/` 定位规则源码。
- 从 `references/parity-matrix.md` 区分已验证兼容、临时实现和有意变化。
- 在浏览器中从标题屏开始一局完整时期战役，执行经营、人才、出征、存档和月度推进。
- 明确下一项改动属于产品玩法、兼容验证还是现代化表现，并把证据记录到相应位置。

如果上述任一项与实际仓库不符，应先更新本文件和 README，再继续扩大实现范围。

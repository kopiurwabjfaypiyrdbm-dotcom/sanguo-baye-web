# 战败俘虏与招降规则定位

本记录只依据已入库、固定提交的 MIT C 核心，约束 Web 战后人员闭环；不包含原始资源或表现资产。

## 战败处理

- `citycmdd.c:FightResultDeal/TheLoserDeal` 对战败方最多 10 名参战武将逐一处理。首次 `gam_rand() % 100` 大于人物智力时直接成为俘虏，否则尝试逃往原势力仍拥有的城市。
- `citycmdd.c:HoldCaptive` 把原所属写入 `OldBelong`、把当前所属设为俘虏哨兵、兵力清零并把人物加入发生战斗的城市。
- 无可逃城市且随机值为 0 时，原版存在战死分支并把装备放回城池。当前 Alpha 暂不实现人物死亡，以免在继承、装备缴获和玩家确认界面完成前产生不可逆损失。
- `KingOverDeal` 在君主被俘或战死且势力仍有城市/人物时另立新君；电脑选择智力最高者，玩家会手动选择。当前 Web 临时规则让仍有退路的君主必定撤退，只有失去最后一城时才会被俘，因此尚未进入继承选择。

## 招降

- `citycmdb.c:SurrenderMake` 从本城俘虏和本城在职武将中各选一人，消耗执行者 4 点体力并进入命令队列。
- `citycmd.c:SurrenderDrv` 先比较双方智力差 `执行者智力 - 俘虏智力 + 50`；第一关失败会直接结束，不降低俘虏忠诚。
- 通过智力关后才把忠诚降低十分之一。旧忠诚高于 60 时不会当次归顺；其余情况下再按人物性格系数和忠诚进行一次随机判定。成功忠诚为 `40 + rand % 40`。
- 当前 TypeScript 在 `core/captiveCommands.ts` 复写主要数值分支，并显式钳制智力概率，避免 C 的 `U8` 回绕成为不可读产品规则。命令立即结算而非进入尚未实现的跨月队列，属于临时差异。

## 当前产品边界

- `Officer.status === 'captive'` 时人物归入无所属桶，同时保存 `captorFactionId`、`formerFactionId` 和羁押城市；完整性校验要求羁押城市由俘虏方持有。
- 快速战斗和手动战斗共用 `applyBattleResult`，使用战斗结果之后的确定性种子进行俘虏判定。守城非参战人员继续撤往己方城市，不进入俘虏抽签。
- 羁押城市再次被占领时，原版人物仍随城市队列保留；Web 会把第三方俘虏的 `captorFactionId` 转交新城主，避免跨月出现“俘虏方已不拥有监牢”的悬空状态。若新城主正是人物被俘前所属势力，则视为救回并恢复在职。
- 玩家可在城池面板招降或释放俘虏；释放是不消耗行动的现代人道选项，转为本城在野人物。处斩、战死、继承选择和装备缴获后置。
- 战略 AI 会优先尝试招降本城低忠诚俘虏，并与玩家使用同一核心命令。
- 中立城池没有可执行羁押的人物势力；进攻中立城失败时，败方不会生成中立势力俘虏。

## 已知随机与配置差异

- C 对每名败方参战者固定先取一次俘虏随机数，并在逃跑时再随机选择目的城；Web 当前为有序确定撤退，并会对受君主保护或无退路分支短路随机调用。因此规则可复演，但随机种子序列尚不宣称与原版逐调用一致。
- 原版占城后对未参战人员的清所属/兵力处理与 Web 的“非参战守将随势力撤退”不同，当前优先保持连续战役的人才可管理性。
- `fixConsumeMoney` 配置开启时，C 的招降命令还校验并扣除金钱；Web 当前没有该兼容开关。原版玩家失败报告另有一次仅用于表现的随机调用，Web 的规则种子不复现这次表现随机。
